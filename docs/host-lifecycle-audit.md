# 三类 ACT Host 生命周期检查（2026-10-10）

本轮重点是用户手动导入插件使用的通用 Host，同时检查共享 Host 和抹茶专用 Host。继承 `7992a99` 的上传器、绝神兵工具适配；两个用户插件仍不随包发布。本轮没有修改版本号或发布。

## 已修复

| 触发条件 | 原行为 | 修复后的行为 |
| --- | --- | --- |
| 停止时，等待 Shutdown ACK 被取消 | 提前退出清理，管道和不配合退出的子进程可能残留 | `finally` 清理 IPC，并独立完成有时限的子进程退出/终止；三个 Host 共用 |
| IPC 序列化、发送线程或看门狗异常 | 发送任务可能已经退出，但收到心跳后仍显示连接正常 | 异常立即上报 Supervisor；健康心跳不能覆盖终止故障，触发既有恢复流程 |
| Host 启动后立即断开 | 后写入的 Connected 状态可能覆盖已发生的故障 | 在启动读写任务前发布 Connected，启动失败清理完整会话 |
| 手动停止通用/抹茶 Host 后修改权限 | 配置刷新可能重新启动已停止的 Host | 区分维护停止和用户停止；初次启动/维护恢复允许自动启动，用户停止或熔断只能显式恢复 |
| 更换 ACT 插件目录后重启 Host | Supervisor 仍使用构造时保存的旧目录 | 三个 Host 每次启动读取当前插件目录 |
| 故障恢复排队期间，用户已经启动新会话 | 旧恢复任务可能停止新进程并消耗新会话重试额度 | 清理和延迟恢复前均校验故障所属会话；新会话在旧恢复任务结束前再次失败也不会丢失恢复请求 |
| 共享/抹茶 Host 启动失败或用完启动时限 | 通用 Host 被前序异常或共用取消令牌阻断 | 每个角色单独计时、单独记录失败；抹茶仍按既有依赖等待共享 Host，通用 Host 独立继续 |

显式安装/启动某类插件允许恢复该插件所属 Host；安装共享 Host 插件不会顺带解除抹茶 Host 的手动暂停。通用插件调用 FoxTTS 仍依赖运行中的共享 Host 语音服务；进程可以独立启动不等于所有跨 Host 服务都没有依赖。

## 验证

- 修改前用反例确认：取消 Shutdown ACK 等待留下活动管道；发送超长帧使写任务退出但没有故障上报。
- 新增 `HostLifecycleSmokeTests`，纳入完整 Package smoke：不响应关闭的真实子进程、真实命名管道、发送异常与看门狗竞态、当前目录重绑定、用户暂停与维护恢复、旧会话恢复隔离、真实通用 Host 崩溃后重新加载插件、各角色启动失败/超时与全局取消。
- 完整 Release 构建：0 警告、0 错误；完整 Package / FFXIV_ACT_Plugin smoke 通过。最终竞态调整后再次构建并通过定向生命周期测试。
- 完整 Host smoke 通过：真实 Triggernometry / PostNamazu / FoxTTS 副本使用隔离配置，包含日志、战斗、区域、TTS 请求/回执、队列、绘图与 U7b 回放；真实抹茶包的独立进程加载、双向网络、通知、权限与卸载通过；通用 Host 授权加载、日志和退出通过。
- 用户提供的原版上传器/绝神兵 DLL 回归通过：真实 V8、配置隔离、日志目录切换、ACT 日志、TTS、权限拒绝和卸载。使用离线合成数据，没有真实 FFLogs 登录/上传或游戏按键。
- 人工审查取消路径、会话归属、暂停状态、三个角色的调用入口与 CI 接入；`git diff --check` 通过。测试结束未遗留 `DalamudActCompat.Host.exe` 进程。

测试结果不能替代真实游戏会话、真实上传或扬声器输出的验收。通用 Host 是完整信任插件进程，不是操作系统沙箱。

## 第二轮：独立审查后的修复（feature/host-lifecycle-fixes）

| 触发条件 | 原行为 | 修复后的行为 |
| --- | --- | --- |
| 自动恢复或内存回收持有 Supervisor 锁时，用户点"停止" | 停止在 10 秒 UI 时限内拿不到锁就被取消，什么也没记录，恢复随后重新拉起 Host | 停止意图在等锁前写入；恢复、启动、重启完成后若发现停止请求，立即关闭刚启动的会话，也不再排队重试 |
| 插件回调卡住 Host 的 IPC 读线程 | 管道无缓冲，下一帧写入一直挂起，已写与已确认序号相等，心跳正常，看门狗永远不报故障 | 记录在途写入的开始时间，超过 15 秒判为故障并走既有恢复（Host 读线程还要回放启动期缓冲事件，取与 Host 插件启动相同的上限，避免误判） |
| 共享 Host 未运行时修改抹茶权限 | 权限刷新直接返回，正在运行的抹茶 Host 保留已撤销的能力 | 抹茶权限变化先停止抹茶 Host，再判断是否能在共享 Host 之后重启 |
| 权限刷新中共享 Host 重启失败或超时 | 共用一个 try 和 20 秒预算，通用和抹茶的权限重启被跳过 | 复用 HostStartupSequence：每个角色独立时限和错误处理，抹茶仍依赖共享 Host |
| 手动云备份后恢复组件，共享或抹茶恢复失败 | 顺序恢复、首个失败即抛出，解析器或通用 Host 保持停止 | 每个组件独立恢复和计时，最后汇总所有失败 |
| 子进程在 Kill 后 1 秒仍未退出 | 清理抛异常，跳过熔断赋值并立即重排，熔断永不打开 | 熔断判定在 finally 中生效，失败的清理也计入重启预算 |
| 关闭简化模式后启动 Host 期间登出 | 启动不可取消，每角色 45 秒，可能使登出等拓扑锁 30 秒超时而漏停 | 该启动使用登录会话令牌，登出即取消 |
| 多阶段权限刷新期间登出（Codex 交叉审查补充） | 刷新只绑定插件卸载令牌，每角色 20 秒串行持锁；登出停止等锁 30 秒后放弃，可能漏停 | 刷新绑定发起时的登录会话令牌，登出即结束；登出/封禁停止改为一直等锁（每 30 秒记录一次），不再放弃 |
| 卸载插件或预检失败后的清理 | 按"用户主动启动"处理，解除通用 Host 的手动暂停 | 只有确认授权插件属于主动启动；卸载和清理按自动启动处理，保留手动暂停 |

新增回归（HostLifecycleSmokeTests）：真实 Host 与无法建立管道的 Host 在恢复启动期间收到超时停止、阻塞的 Host 读线程、清理持续失败时打开熔断；以及直接调用 Plugin 入口的"多阶段权限刷新中登出"（未修复时登出等待 10.0 秒，修复后 5 秒内完成且三个 Host 均停止）。

## 第三轮：Codex 一次性复查（R1–R4）

四项均为 dc45091 已有问题，本轮逐项核对源码后修复：

| 编号 | 触发条件 | 原行为 | 修复后的行为 |
| --- | --- | --- | --- |
| R1 | 出厂重置已取得文件操作锁，在等待拓扑锁时超时或取消 | 文件操作锁不释放，之后云文件/Cactbot 操作在重载前一直拿不到锁 | 每把锁各自记录是否取得，finally 只释放已取得的锁；Host 快照读取也在保护范围内 |
| R2 | 随包安装恢复运行时与登出交错 | 登出先停解析器再等拓扑锁；安装恢复随后重新启动解析器，登出结束后解析器仍在运行 | 登出拿到拓扑锁后再停一次解析器，与所有恢复解析器的维护操作串行；随包安装、出厂重置、云文件操作的恢复都绑定发起时的登录会话，协调器在每个恢复阶段前重新检查，快速重新登录也不会接上旧会话的恢复；文件回滚照常完成 |
| R3 | 内存回收任务排在重启之后，重启已换上新会话 | 旧任务停掉新会话的 Host 并启动另一个，还占用新会话的回收额度 | 排队时记录触发会话，拿到锁后会话不符即放弃；占位标记照常释放，新会话之后的内存压力仍能触发回收 |
| R4 | RestartAsync 停止阶段收到外部 StopAsync 且其等锁超时 | 重启把自己的停止标记清掉，外部停止意图丢失，Host 重新运行 | 用停止请求计数区分重启自身的停止与外部停止；有外部停止时重启放弃启动，异常分支也不再无条件清除停止标记 |

R4 的组件契约缺口已修。目前 Plugin 中 RestartAsync 只在权限刷新里调用，与 UI 停止都持拓扑锁，现有界面按钮未必会走到这个顺序。

拓扑锁：登出/封禁停机继续一直等待，不再放弃。各持锁操作只有协作式时限，同步的解析器停止或文件操作可能超出时限，所以这不是硬性上限。各入口现在记录持锁操作名和开始时间，等待超过 30 秒时日志会写明正在等哪个操作。尚未细到阶段级别。

新增回归（HostLifecycleSmokeTests）：
- 出厂重置在等第二把锁时取消，以及正常完成后两把锁均释放。
- 随包安装恢复期间登出，覆盖恢复共享 Host 时、恢复解析器前、快速重新登录、不认会话的恢复者四个场景。
- 旧会话内存回收排在重启之后，使用真实 Host 和合成样本；当前会话的内存压力仍能回收。
- 重启停止阶段收到超时的用户停止，使用真实 Host。

每项回归都临时去掉对应防护验证过会失败，恢复后通过。出厂重置失败回滚中的解析器恢复改由会话令牌约束，复用了 FactoryResetService 既有的令牌语义测试，没有单独加回滚注入测试。

第三轮时待验证：Supervisor 的故障恢复和内存回收用 Task.Run 启动，任务没有保存，卸载时只做 2 秒停止尝试。该项已在下方发布复核中复现并修复。

## 0.4.5.9 发布复核：自动恢复与卸载收尾

- 使用真实 IPC 管道和不响应退出的隔离子进程，在故障恢复进入强制清理前发起卸载。旧实现记录 `ObjectDisposedException (SemaphoreSlim.Release)`：2 秒等待结束后先释放了恢复任务仍持有的锁。
- Supervisor 现在在同一调度锁内登记恢复任务、关闭新任务入口并取得卸载快照；取消后汇合所有已登记恢复，再执行最终停止与资源释放。日志计时器也等待在途回调结束，不与已释放 IPC 交错。
- 新增长期回归 `UnloadDuringRecoveryAsync`，覆盖故障恢复和内存回收两个入口，要求卸载返回时子进程停止、恢复完成且无清理异常；外部同场景旧实现失败、修复后通过。完整 PackageSmoke（含 14 组生命周期回归）通过。
- 同时修正账号界面源码检查中遗留的全局弹窗方法名，断言当前窗口内绑定入口。界面本身仍由原生鼠标放行、布局及绑定状态测试验证。
- 此修复不以超时跳过清理；解析器同步清理、真实游戏内操作及长期运行仍属于各自的验证边界。
